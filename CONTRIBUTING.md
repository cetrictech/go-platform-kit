# Contributing

Use a supported patched Go line from [support policy](docs/support-policy.md). Run ordinary tests without infrastructure through `make test`; run real services with `make services`, `make integration`, and `make services-down`. A release requires the full `scripts/release-check.sh` gate, not a local unit result. No tags or publication are authorized by ordinary implementation work.

For every public change, update [API contracts](docs/public-api-contracts.md): concurrency mode, cancellation/remote outcome, ownership/cleanup, accepted-work bounds, error/wire behavior and driver boundary. Keep interfaces small; introduce an optional interface rather than requiring all external implementations to add a method. Do not add optional drivers to root dependencies. Avoid a new native-driver type in a public signature when an SDK value or small consumer interface suffices. Review approved native escape hatches explicitly.

Run `scripts/check-api.sh` against the previous module-specific stable tag, contract tests, race/vet/static/vulnerability checks, critical-path benchmarks and `scripts/check-independent.sh` outside the workspace. Real adapter changes need real infrastructure and fault/cleanup tests, including network outages, restarts, Kafka rebalances and credential rotation where applicable. Tests must demonstrate bounded queues, goroutine/connection cleanup and meaningful failure semantics; mocks alone are insufficient.

Follow [semantic and Go import versioning](docs/versioning.md), independently version modules, and update [the matrix](docs/compatibility-matrix.md) plus `release/modules.json` when versions/dependencies change. Document deprecations and concrete migration examples before removing an API or changing a response/error contract. Preserve existing stable fixtures. Dependency upgrades follow [the upgrade/remediation policy](docs/dependency-policy.md); do not regenerate a performance/API baseline merely to hide a regression.

Required hosting checks and release identity/tag protection are maintainer-owned server settings; repository workflows alone cannot prove they are enabled. v1 admission also requires reviewed results from real independent consuming projects in `release/consumers.json`; repository examples and generated import tests do not count.
